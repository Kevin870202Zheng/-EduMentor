1. 产品愿景与定位

1.1 现状问题

EduMentor v1.0 的核心产品形态是"诊断 → 推荐路径 → 做题 → 答疑 → 复盘"。学生的主要学习活动是做题和对话。这种形式存在以下不足：

  • 缺乏知识传授环节：学习路径节点仅展示"做题验证"，缺少"教师讲授"的过程
  • 学习体验单一：界面以列表、表格、对话气泡为主，缺乏沉浸感
  • 多Agent优势未发挥：当前仅支持单Agent答疑（苏格拉底式引导），没有课程中的多角色互动
  • 知识呈现方式单一：知识点以文本卡片展示，缺少白板、公式推导、可视化等教学手段

1.2 产品愿景

一句话愿景：让每个学生拥有一位AI教师，自动根据薄弱点为TA生成专属课堂，边学边练，让知识从"被验证"到"被教授"。

核心体验升级：

┌─────────────────────────────────────────────────────────────┐ │ v1.0 体验: │ │ 打开App → 学习路径列表 → 选节点 → 做题 → 错了？→ 去答疑 │ │ ↓ │ │ v2.0 体验: │ │ 打开App → 智能诊断薄弱点 → AI教师自动生成今日课堂 → │ │ 开始播放授课 → AI教师讲解 + 白板演示 + 穿插Quiz确认理解 → │ │ AI同学提问引发讨论 → 苏格拉底导师引导反思 → │ │ 下课前总结 + BKT更新 → 课后自适应练习题 → 完成 │ └─────────────────────────────────────────────────────────────┘

1.3 目标用户

用户痛点v2.0 解决
高校学生 自学缺乏教师引导，做题遇到难点无讲解，容易卡住放弃 AI教师自动生成课堂，主动讲解而不是被动等待提问
自学备考者 需要系统化的知识讲解，而非碎片化做题 知识点→课堂的自动转化，像真实上课一样系统学习
教师 需要了解学生的薄弱点和课堂学习表现 驾驶舱增加"课堂完成度"、"课堂Quiz正确率"等学情指标

2. 用户故事

📖 故事 1：小明的第一堂薄弱点补强课
角色：学生 | 触发条件：完成BKT诊断后

小明登录EduMentor，系统诊断出他在"微积分"课程的"链式求导法则"掌握度仅38%（薄弱知识点）。系统自动为该薄弱知识点生成了一堂15分钟的补强课——包含概念回顾、白板推导演示、三道渐进式Quiz。小明点击"开始学习"，AI教师开始讲解，每一步配合白板动画。讲解到第二道Quiz时，AI同学"小E"主动提问："为什么这里要用链式法则而不是乘法法则？" AI教师暂停，给予进一步的推导说明。答对所有Quiz后，BKT更新链式法则掌握度至72%。系统提示："知识点提升显著，是否继续下一课'隐函数求导'？"

📖 故事 2：小红的主动预习课堂
角色：学生 | 触发条件：主动选择知识点进入课堂

小红下周要学"概率论-贝叶斯公式"，选择该知识点→点击"生成预习课堂"。系统5秒内生成了4个教学场景：(1) 问题引入（用经典例子激发兴趣），(2) 公式推导（含白板动画），(3) 应用示例（含互动Quiz），(4) 总结与前置知识链接。小红边听边做笔记，遇到不理解的公式可以随时暂停并语音提问。课堂结束后，系统记录了小红在Quiz中的表现，推荐了相关的前置知识点复习。

📖 故事 3：小刚的课后复习+做题组合
角色：学生 | 触发条件：完成课堂学习后

小刚完成了"线性代数-矩阵乘法"课堂后，系统自动为他生成了5道针对性的练习题（基于课堂中Quzi答错的变体）。小刚做题时，每道题旁边都关联了课堂中的对应讲解片段——点击"回顾课堂"即可回看AI教师的对应讲解。做完所有题后，复习报告显示：课堂中的薄弱点在课后练习中正确率提升了40%。系统建议明天再进行一次间隔复习。

📖 故事 4：教师的课堂学情总览
角色：教师 | 触发条件：查看班级学情

李老师打开教师驾驶舱，看到"课堂学习"栏目：全班30人中有28人完成了"微积分-不定积分"的AI课堂，平均Quiz正确率82%。筛选出正确率低于60%的6位学生，可以看到他们在具体哪个教学场景中卡住了（例如："场景3：换元积分法"的Quiz答对率仅35%）。李老师据此决定下节课重点讲解换元积分法，并推送给这6位学生一份补充题。

3. 核心功能需求

3.1 课堂生成管线 新增

3.1.1 功能概述

基于课程知识图谱（KnowledgePoint + KnowledgeRelation），自动生成结构化课堂教学内容。这是整个v2.0的基础设施。

3.1.2 核心流程

┌───────────────────────────────────────────────────────────────────────┐ │ 输入: 知识点ID (或知识点集合) + 学生学习画像 (BKT状态) │ │ │ │ 阶段1: 课堂大纲生成 (SceneOutline) │ │ ───────────────────────────────────────────────────────────────── │ │ 输入 → LLM 分析知识点 → 生成 3-8 个教学场景大纲 │ │ 每个大纲: { type, title, description, keyPoints, teachingObjective } │ │ 场景类型: slide(讲解) | quiz(练习) | interactive(互动) │ │ 输出: SceneOutline[] │ │ │ │ 阶段2: 场景内容生成 (Scene) │ │ ───────────────────────────────────────────────────────────────── │ │ 每个大纲 → LLM 生成完整场景内容 │ │ Slide场景: 讲解文本 + 教学动作序列 (speech/白板/高亮...) │ │ Quiz场景: 题目 + 选项 + 答案 + 讲解 │ │ Interactive场景: 互动内容 + 引导逻辑 │ │ 输出: Scene[] (含 Action[]) │ │ │ │ 阶段3: 持久化 │ │ ───────────────────────────────────────────────────────────────── │ │ 保存到数据库: classroom + scene + action + scene_quiz │ │ 关联: classroom ↔ course ↔ knowledge_point │ └───────────────────────────────────────────────────────────────────────┘

3.1.3 生成策略

策略适用场景说明
逐场景按需生成 首次观看 只生成下一个场景（降低首屏等待），学生学完时后台预生成下一个
全量预生成 教师备课/离线导出 一次性生成所有场景，适合需要检查内容的教师
增量补强生成 复习/补强 基于已有课堂，仅针对薄弱知识点新增/替换场景

3.1.4 知识点→课堂大纲的提示词策略

输入元素说明
KnowledgePoint.name + description核心教学内容
KnowledgeRelation (PREREQUISITE/SUBSUMED_BY)前置/后置知识链接（用于课堂定位和回顾）
BKT 掌握度 (mastery)学生当前掌握水平，控制讲解难度和深度
错题历史 (error_records)学生曾做错的题目相关知识点，作为重点讲解方向
CourseMaterial (教材资料)引用教材原文/示例，增强课堂权威性

3.2 Playback 播放引擎 新增

3.2.1 功能概述

前端沉浸式播放器，逐场景播放教学内容，按Action顺序驱动教学动作。核心体验是"像看视频一样上课"，但内容是AI实时生成的交互式课堂。

3.2.2 状态机设计

start() pause() idling ──────────────────→ playing ──────────────→ paused ▲ │ │ │ finish() │ resume() │ └───────────────────────────┘───────────────────────┘ │ userInterrupt() ▼ live ──────────────→ paused ▲ pause() │ │ │ └────────────────────┘ resume / user msg 状态说明: - idling: 初始/结束，等待用户点击"开始" - playing: 自动播放中，按顺序消费 Scene[].Action[] - paused: 用户主动暂停/系统暂停等待用户操作（如完成Quiz） - live: 讨论模式——学生打断发言/回答问题后，Agent接管对话流

3.2.3 播放控制

控制行为优先级
▶ 开始/继续从当前暂停的场景继续播放下一个ActionP0
⏸ 暂停停止当前Action执行，保存播放位置P0
⏭ 下一场景跳过当前场景剩余Action，进入下一个场景P1
⏮ 上一场景回到上一个场景从头播放P1
🙋 举手提问中断播放 → 进入 live 模式 → 学生输入问题 → Agent回答 → 恢复播放P0
📌 场景选择直接跳转到任意场景（不一定要按顺序播放）P2

3.2.4 播放器UI构成

  • 主播放区：展示当前场景的内容（讲解文本、白板、Quiz、互动组件）
  • 场景导航：顶部/侧边显示场景列表（已完成/当前/未完成状态），可点击跳转
  • 控制栏：播放/暂停/上一场景/下一场景/进度条/TTS开关
  • AI角色展示：当前发言Agent的头像、名字、角色（教师/同学/导师）
  • 讲解区：AI教师的当前讲解文本（流式显示或逐步显示）
  • 交互区：白板绘图区域 / Quiz作答区域 / 互动仿真区域

3.3 多Agent教学交互 新增

3.3.1 角色体系

角色职责交互方式
🧑‍🏫 AI教师 (Teacher) 主讲人：讲解概念、推导公式、演示示例、主持课堂节奏 自动播放讲解 + 白板演示 + 提问引导，学生可随时打断提问
🧑‍🎓 AI同学 (Classmate) 学习伙伴：提出疑惑、展示错误思考过程、降低学生心理压力 在课堂中适时"举手"提问："老师，为什么这里不能直接用这个公式？"
🧑‍🏫 苏格拉底导师 (Tutor) 引导者：通过追问引导学生自己发现问题、反思总结 在Quiz答错后介入："你的答案是这样的，那我问你——这个公式的前提条件是什么？"

3.3.2 交互流程

┌────────────────────────────────────────────────────────────┐ │ 正常播放模式 (playing): │ │ AI教师按Action顺序讲解 → 每个Action渲染完成后自动下一个 │ │ → 遇到QuizAction → 暂停等待学生作答 → 根据答对/错触发反馈 │ │ → 继续下一个Action │ │ │ │ 讨论模式 (live): │ │ 学生打断/提问 → 暂停播放 → Director决定谁发言 │ │ → Agent生成回答 + 可能的动作(白板/高亮) │ │ → 多轮对话直到学生满意 → 恢复播放 │ │ │ │ AI同学触发: │ │ 在预设时机（讲解完复杂概念后）→ Director让AI同学"举手" │ │ → AI同学提一个问题 → AI教师解答 → 继续 │ └────────────────────────────────────────────────────────────┘

Java 实现方案：使用状态模式实现 Director-Agent 循环，调用现有 LLMService 做决策和内容生成，保持 Spring Boot 统一技术栈。

  • DirectorService：决定当前场景的下一个Action/下一个Agent角色
  • AgentService：根据角色和上下文生成教学内容文本+动作指令
  • PlaybackController：管理播放状态，协调Action执行顺序

WebSocket 事件推送：

  • text_delta：流式讲解文本
  • action：执行某个教学动作（白板绘图/高亮/Quiz...）
  • agent_start / agent_end：Agent发言开始/结束
  • scene_change：场景切换
  • cue_user：等待学生操作

3.4 课堂内Quiz与BKT联动 新增

3.4.1 联动逻辑

课堂Quiz提交 │ ├── 答对 → 通知BKT引擎 (正确响应) → BKT更新知识点掌握度 │ → 掌握度 > 阈值 → 自动跳过后续same-KP的简单Quiz │ → 课堂自适应缩短 │ └── 答错 → 通知BKT引擎 (错误响应) → BKT更新知识点掌握度 → 记录到 error_records (关联课堂ID+场景ID) → AI教师补充讲解该知识点 → 生成一道同类变体题验证是否理解

3.4.2 课堂与错题联动的复习

场景示例：

小刚在"矩阵乘法"课堂的场景3 Quiz中答错了一道关于"矩阵乘法结合律"的题目。系统自动：

  1. 将该题加入 error_records，标记来源为课堂
  2. 生成一条错题记录，附带此知识点的课堂讲解片段引用
  3. 在复习模式下，展示错题时提供"回放课堂讲解"按钮
  4. 基于艾宾浩斯遗忘曲线，在合适的时间提醒复习

3.5 学练结合流程 新增

3.5.1 完整学习闭环

┌──────────────────────────────────────────────────────────────────┐ │ 完整的"学→练→测→复盘"闭环 │ │ │ │ ① 学情诊断 → BKT识别薄弱点 → 弱在哪？ │ │ ↓ │ │ ② 课堂生成 → 针对薄弱知识点生成3-5个教学场景 │ │ ↓ │ │ ③ 课堂播放 → AI教师边讲边练 + 穿插Quiz │ │ ↓ │ │ ④ Quiz反馈 → BKT实时更新知识点掌握度 │ │ ↓ │ │ ⑤ 课后练习 → 基于课堂Quiz答错生成5道变体练习题 │ │ ↓ │ │ ⑥ 结果分析 → 对比"课堂Quiz vs 课后练习"掌握度变化 │ │ ↓ │ │ ⑦ 下一课规划 → 根据最新BKT状态调整后续学习路径 │ └──────────────────────────────────────────────────────────────────┘

3.5.2 学习路径的升级

v1.0 的学习路径节点（LearningPathNode）仅指向"做题验证"。v2.0 升级为三种节点类型：

节点类型含义用户操作
classroom沉浸式课堂学习节点进入课堂播放器，自动播放教学
quiz练习验证节点（现有方式）做题 → 提交 → 看解析
review复习+复盘节点课堂片段回放 + 错题重做

3.5.3 "学练结合"UI设计

  • 学习模式选择：学生进入课程后，可选择"课堂学习"或"直接做题"两种模式
  • 课堂播放器内嵌练习：课堂过程中自动穿插Quiz场景，完成后自动继续
  • 知识点关联：每道课后练习题旁边标注"关联课堂片段"，点击可回放AI教师对应讲解
  • 进度同步：课堂完成度 = 已学场景数 / 总场景数；练习完成度 = 已做题数 / 总题数

3.6 教学动作系统 新增

3.6.1 动作类型定义

动作类型含义前端行为优先级
speechAI教师讲解显示讲解文本（可配合TTS朗读）P0
speech_with_highlight带高亮的讲解讲解文本同时高亮屏幕上的关键元素P1
wb_draw_text白板书写文字在白板上逐字写出公式或要点P1
wb_draw_diagram白板画图在白板上画出图表/流程图P2

discussion触发讨论AI同学提问，或邀请学生思考P1
scene_transition场景过渡显示场景切换动画/标题P1

code_demo代码演示显示代码片段并逐行高亮P2

3.6.2 Action 数据格式

// 后端LLM生成的结构化输出 { "sceneId": "uuid", "order": 1, "actions": [ { "type": "speech", "text": "同学们好，今天我们来学习链式求导法则。首先，让我们一起回顾一下什么是复合函数。", "duration": 5000 }, { "type": "wb_draw_text", "content": "如果 y = f(g(x))，则 dy/dx = f'(g(x)) · g'(x)", "position": "center" }, { "type": "speech", "text": "这个公式的意思是：外层函数的导数乘以内层函数的导数。我们来看一个例子。", "duration": 4000 }, { "type": "quiz", "question": "求 y = (2x+1)³ 的导数", "options": ["...", "6(2x+1)²", "3(2x+1)²", "6x+3"], "correctIndex": 1, "explanation": "外层f(u)=u³ → f'=3u², 内层g(x)=2x+1 → g'=2, 相乘得6(2x+1)²" } ] }

3.6.3 前端渲染流程

场景加载 → 按顺序消费 actions[]: │ ├─ speech → 讲解区显示文本，同时可选TTS朗读 │ → 等待 duration 毫秒 → 自动下一个Action │ ├─ wb_draw_* → 白板区域执行绘图操作 │ → 完成后自动下一个Action │ ├─ quiz → 显示Quiz组件 → 等待学生提交答案 │ → 根据答对/错 → AI教师反馈 → 继续 │ → 若答错 → 可能插入补充讲解Action │ └─ discussion → 显示AI同学"举手"提示 → 播放AI同学提问 → 等待学生回应或自动继续

7. 技术约束与决策

7.1 技术栈限制

  • 后端：Java 21 + Spring Boot 3.3.5（必须保持，不得引入 Python/Node 后端服务）
  • 前端：React 18.3 + Vite 5 + Ant Design 5.20 + Zustand（课堂播放器考虑到交互复杂度，建议引入状态管理库）
  • 数据库：PostgreSQL 16 + pgvector
  • 实时通信：WebSocket（已有基础设施）

7.2 关键设计决策

决策选项选择理由
多Agent编排 LangGraph vs Java状态机 Java状态机 保持统一技术栈。使用 Spring State Machine 或自实现状态模式，调用现有 LLMService
课堂生成策略 全量预生成 vs 逐场景按需 逐场景按需 降低首次加载时间，首屏加载3秒内可看。后台异步生成后续场景
场景存储格式 JSONB vs 独立表 独立Scene表+JSONB 场景元数据用独立字段（id/type/order等），场景内容用JSONB。兼顾查询性能和灵活性
实时推送方式 SSE vs WebSocket WebSocket EduMentor 已有 WebSocket 基础设施，双工通信对课堂交互（学生打断+Agent回复）更自然
前端课堂状态管理 React Context vs Zustand Zustand 课堂播放器状态复杂（播放状态/场景列表/进度/Action队列），Zustand 比 Context 性能更好、代码更简洁
白板实现 Canvas vs SVG vs React组件 React组件+SVG 初期白板场景以文字/公式/简单图表为主，React组件+SVG足以应对。Canvas留作未来互动仿真使用

7.3 LLM 结构化输出设计

需要增强现有 LLMService 以支持结构化输出解析：

现有: LLMService.call(request: LlmRequest) → String (原始文本) 增强: LLMService.generateStructured<T>(request: StructuredRequest<T>) → T - 支持 JSON schema 定义输出格式 - 内置重试 + 格式校验 - 错误时提供 fallback 默认值 具体应用: - SceneOutlineGenerator: 输入知识点 → 输出 SceneOutline[] - SceneContentGenerator: 输入 SceneOutline → 输出 Scene (含 Action[]) - QuizGenerator: 输入知识点+难度 → 输出 QuizQuestion[] - DirectorDecider: 输入课堂上下文 → 输出 下一位Agent/Action决定

9. 非功能性需求

9.1 性能

  • 首次场景生成：LLM 生成场景大纲 ≤ 5秒，生成第一个场景内容 ≤ 8秒
  • 场景切换：播放器场景切换 ≤ 500ms（使用预加载策略）
  • WebSocket 延迟：Action 事件从触发到前端渲染 ≤ 200ms
  • 并发课堂：单个服务器支持 ≥ 30 个并发课堂播放（主要瓶颈在 LLM 调用，使用缓存+队列）
  • 数据库查询：课堂加载 < 100ms（含所有场景和Action）

9.2 可扩展性

  • Action 类型可插拔：新增 Action 类型只需注册前端渲染器，后端 Action 表类型字段用枚举+JSONB
  • Agent 角色可配置：Agent 角色列表应支持配置化，可在 application.yml 中定义
  • 生成策略可切换：支持逐场景/全量/增量生成策略的运行时切换

9.3 数据一致性

  • 课堂生成是异步任务，需保证生成完成后的数据一致性（使用数据库事务）
  • 课堂内Quiz提交需同步更新 BKT 和 error_records（使用 @Transactional）
  • 播放进度支持断点续播，以服务端持久化进度为准

9.4 安全性

  • LLM 生成的课堂内容需做基本的安全过滤（避免敏感/不当内容）
  • 课堂内容应基于学生身份做访问控制（只能访问已选课课程的课堂）
  • 课后练习题应基于学生已完成的课堂生成，避免题目泄露

9.5 可观测性

  • 课堂生成任务增加日志埋点：生成耗时、token消耗、重试次数
  • 课堂播放增加事件埋点：场景耗时、Action执行延迟、学生打断频率
  • 新增 Actuator 指标：classroom_generation_duration、classroom_playback_concurrent、quiz_submit_count

集成点说明
BKT 引擎课堂Quiz结果作为BKT的观察值（observation）输入。答对→正确响应，答错→错误响应，更新知识点掌握度
知识图谱课堂生成时读取 KnowledgeRelation 作为上下文。课堂中引用前置知识时，提供"点此复习"链接

🚀 总结：EduMentor v2.0 不是重写，而是在现有基础上叠加课堂能力层。学生端的核心入口升级为"课堂学习+课后练习"双模式，教师端增加课堂维度的学情数据。数据模型扩展 5 张新表，改造 3 张现有表。后端核心增加课堂生成管线、Playback 控制器、多Agent编排；前端核心增加课堂播放器、课堂内Quiz组件、WebSocket课堂频道。
