目标：在已生成的智慧课堂上提供「课前/课后」双阶段模拟法庭，学生扮演法官，AI 扮演原被告，并生成两份判决的分析报告

1. 功能概述

一句话：给每个智慧课堂加一个「法庭直播间」——AI 按课程内容生成案件，学生在聊天室里当法官主持庭审、做判决，课前课后各判一次，AI 对比两次判决出分析报告。

核心价值：把「学知识」变成「用知识判案」——课前判决暴露认知盲区，课后判决检验学习效果，报告呈现成长轨迹。

3. 核心设计：一个案件，两场庭审，一份报告

关键决策：课前与课后使用同一个案件（进入课前法庭时生成并冻结）。理由：

  • 两份判决针对同一案件才有可比性，AI 报告才能呈现「认知变化轨迹」
  • 避免课后二次生成案件的随机性干扰评估

双阶段判定：

阶段触发条件入口
🎭 课前法庭（PRE）课堂存在 & 学生尚未学完（progress != completed）课堂列表卡片「🎭 模拟法庭」按钮
🎭 课后法庭（POST）课堂 progress.status == completed（学完）课堂列表卡片「🎭 模拟法庭」按钮（✅ 已确认：仅课堂列表卡片一处入口）
📌 允许学生在学完前先体验课前法庭（认知摸底）；学完后再开课后法庭。两次判决都提交后，报告入口自动出现。

4. 模拟法庭状态机

CASE_GENERATING 生成案例→ OPENING 宣布开庭→ HEARING 庭审对抗→ JUDGMENT_READY 等待判决→ JUDGED 已判决→ REPORTED 报告生成
状态说明由谁触发
CASE_GENERATINGAI 按课堂内容生成案件（事实/争议焦点/法条/原被告设定）学生首次进入 → 系统调 LLM（约 10-20s）
OPENING系统（书记员）宣读开庭词 + 案情简介，原告做首次陈述案例生成完成自动进入
HEARING庭审对抗：原告陈述 → 被告答辩 → 举证质证 → 法庭辩论；AI 交替扮演双方，学生以法官身份发言/提问/主持庭审对话循环
JUDGMENT_READY庭审结束，学生作为法官提交判决书（结构化：判决结果 + 理由）学生点「提交判决」
JUDGED判决书已保存；若两份判决（PRE+POST）齐全 → 报告可生成判决提交后自动
REPORTEDAI 生成「两次判决分析报告」（认知变化/知识掌握/建议）两份判决齐全后自动触发或手动生成

5. 庭审对话引擎（AI 角色化）

5.1 角色设定

角色扮演者职责
🧑‍⚖️ 法官学生主持流程、向原被告提问、最终判决
⚖️ 原告（AI）LLM（system prompt = 原告角色卡）陈述主张、举证、回应法官与被告
⚖️ 被告（AI）LLM（system prompt = 被告角色卡）答辩、反驳、回应法官与原告
📜 书记员（系统）前端+后端模板开庭词、流程节点播报、庭审记录归档

5.2 AI 对抗机制

  • 角色切换：每个角色持有独立 system prompt（角色卡：立场 + 性格 + 案件信息 + 庭审规则），用 LLMService.chat() 多轮调用
  • 上下文：每次调用携带「案件 + 全部庭审历史 + 最新发言对象」，保证记忆连贯
  • 庭审节奏（提示词约束 + 服务端编排）：
    原告陈述→ 被告答辩→ 原告举证质证→ 被告反驳→ 法庭辩论（1-2 轮）→ 法官（学生）判决
  • 法官自由度：学生可随时发言打断（提问原告/被告、宣布进入下一环节、直接判决）；AI 被告知「法官的指令优先于流程」

5.3 消息模型

📜 书记员：现在开庭。原告赵某诉被告某公司名誉权纠纷一案……
⚖️ 原告：法官大人，被告在公开平台发布不实言论，损害了我的名誉……
⚖️ 被告：我方认为发布内容有事实依据，且属于合理评价……
🧑‍⚖️ 法官（你）：请原告出示证据原件。

6. 数据模型（V21 迁移）

-- ① 模拟法庭会话（每个学生每个课堂两个：PRE/POST）
CREATE TABLE moot_court_sessions (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    classroom_id UUID NOT NULL REFERENCES classrooms(id),
    student_id  UUID NOT NULL REFERENCES users(id),
    phase       VARCHAR(8)  NOT NULL CHECK (phase IN ('PRE','POST')),
    status      VARCHAR(20) NOT NULL DEFAULT 'CASE_GENERATING'
                CHECK (status IN ('CASE_GENERATING','OPENING','HEARING',
                                  'JUDGMENT_READY','JUDGED','REPORTED')),
    case_content JSONB,               -- AI生成的案件：事实/争议焦点/法条/原被告设定
    judgment    TEXT,                 -- 学生判决书（结构化 JSON：result + reason）
    report      TEXT,                 -- AI 分析报告（两份判决对比）
    stage_index INTEGER DEFAULT 0,    -- 当前庭审环节（0陈述/1答辩/2举证/3辩论/4判决）
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE (classroom_id, student_id, phase)
);

-- ② 庭审消息（独立表，便于审计/分页/未来回放）
CREATE TABLE moot_court_messages (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id  UUID NOT NULL REFERENCES moot_court_sessions(id) ON DELETE CASCADE,
    role        VARCHAR(16) NOT NULL,  -- SYSTEM/CLERK/PLAINTIFF_AI/DEFENDANT_AI/JUDGE_STUDENT
    content     TEXT NOT NULL,
    round_seq   INTEGER NOT NULL,      -- 庭审轮次
    created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_mcm_session ON moot_court_messages (session_id, round_seq);

7. API 设计

# ── 法庭会话 ──
POST /api/moot-courts/{classroomId}/start?phase=PRE|POST
     # 获取或创建法庭；首次进入触发案例生成（同步等待 LLM，约 10-20s）
     # 返回 { sessionId, status, caseContent, messages:[...] }
GET  /api/moot-courts/{classroomId}/session?phase=PRE|POST
     # 查询会话（含案例/状态/消息列表/判决/报告状态）

# ── 庭审对话（核心） ──
POST /api/moot-courts/{classroomId}/message
     Body: { phase, content }        # 法官（学生）发言
     # 服务端编排：记录法官发言 → 决定轮到原告/被告 → 调 LLM 生成回应
     # 返回 { messages: [法官发言, AI回应(原/被告)], stageIndex, nextSpeaker }
     # 支持可选参数 action: "next_stage"（进入下一庭审环节，由书记员播报）

# ── 判决与报告 ──
POST /api/moot-courts/{classroomId}/judgment
     Body: { phase, result, reason } # 判决结果 + 判决理由（结构化）
POST /api/moot-courts/{classroomId}/report
     # 生成分析报告（要求 PRE+POST 两份判决齐全；AI 对比生成）
GET  /api/moot-courts/{classroomId}/report
     # 获取报告（含两份判决 + 报告正文）

8.3 分析报告页（MootCourtReport）

  • 左右对比：课前判决 vs 课后判决（并排展示）
  • AI 报告三段式：认知变化轨迹（从课前到课后观点/理由变化）→ 知识掌握评估（对照课堂知识点逐项）→ 学习建议
  • 支持复制/下载报告文本

9. 权限与数据归属

  • 法庭会话按 student_id 隔离，学生只能访问自己的法庭
  • 课堂未发布/不存在 → 不可进入
  • 课后法庭判定以 classroom_progress.status == completed 为准（服务端校验，不信任前端）
  • 报告生成前校验两份判决均存在

11. 风险与假设

  • R1 案例生成质量：课堂内容若过短，AI 可能生成泛化案例 → 素材不足时提示「课堂内容较少，案例为通识性案件」
  • R2 LLM 角色一致性：长对话中原被告可能串角色 → 系统 prompt 强约束 + 消息 role 前缀，必要时每次调用重新注入完整案件+历史
  • R3 庭审时长：完整庭审需多轮 LLM 调用（每次 3-8s）→ 设置轮次上限（如每环节最多 2 轮），保证 10 分钟内完成
  • R4 报告对比失真：若学生课前课后判决相同 → 报告明确说明「未发生认知变化」，避免强行解读
  • H1 假设：课堂关联的知识点内容足以支撑案件生成 —— 若课堂未关联知识点，退化为「按课堂名 + 场景讲解文本」生成通识性案件

12. 待确认决策点

① 课前/课后用同一案件？
✅ 已确认：同一案件（两份判决对比才有意义，报告可呈现成长轨迹）。
② 庭审推进方式？
✅ 已确认：AI 自动推进 + 学生可干预（AI 每轮结尾提示下一环节；学生可随时发言或点「下一环节」）。
③ 判决书形式？
✅ 已确认：结构化（判决结果单选：支持原告诉请 / 驳回诉讼请求 / 部分支持 + 理由文本框），便于报告对比。
④ 报告生成时机？
✅ 已确认：两份判决齐全后，学生在报告页点击「生成报告」（LLM 约 15-25s），避免自动生成浪费。
⑤ 案例生成素材范围？
✅ 已确认（调整）：以课堂关联的知识点为素材构造案例（知识点名称+内容 → AI 构造贴合知识点的案件）；课堂未关联知识点时退化为通识性案件。
⑥ 入口位置？
✅ 已确认（调整）：仅课堂列表卡片一处（按进度状态显示 PRE/POST 按钮；不再加播放器内入口）。
