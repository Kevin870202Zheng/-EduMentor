🔗 退课联动分析报告

项目：EduMentor 智学导师 · 范围：学生端 · 日期：2025-06-25
⚠️ 核心结论：当前退课逻辑（EnrollmentService.dropCourse）仅将 student_courses.status 标记为 "dropped"，未做任何联动处理。涉及 8 个功能模块/数据域，其中 3 个存在关键数据一致性问题，2 个存在功能性缺陷，2 个需做前端UI联动。

🔍 逐项详细分析

1️⃣ MainLayout 课程上下文 严重

问题描述：MainLayout.jsx 的 selectedCourseId 是全局上下文状态，所有子页面（学情总览、学习路径、QA、错题复盘）都依赖它。退课后如果当前选中的恰好是被退的课程，selectedCourseId 仍指向已退课程的ID，各子页面会发送无效的API请求。

代码位置：frontend/src/components/common/MainLayout.jsx:44-57

// 只在组件挂载时加载一次，不会因退课而刷新 useEffect(() => { if (role === 'student' && user?.id) { enrollmentAPI.listByStudent(user.id).then(res => { const list = res?.data || res || []; setStudentCourses(list); const saved = localStorage.getItem('currentCourseId'); // ❌ 如果saved指向已退课程，这里不会清理 if (saved && list.some(c => c.courseId === saved)) { setSelectedCourseId(saved); } else if (list.length > 0) { setSelectedCourseId(list[0].courseId); // 只有首次加载会触发 } }).catch(() => {}); } }, [user?.id]); // 依赖是 user.id，不是 studentCourses

影响链：

  • 学情总览 → 请求 /api/diagnosis/analyze?courseId={已退课程} → 返回空数据
  • 学习路径 → 请求 /api/paths/plan?courseId={已退课程} → 可能报错或返回不应展示的数据
  • 智能答疑 → 使用已退课程的 courseId 做 RAG → 不应该允许继续提问
  • 错题复盘 → 请求 /api/reviews/errors?courseId={已退课程} → 数据残留问题

建议方案：

  • 退课API返回后，前端主动触发重新加载选课列表
  • 如果当前 selectedCourseId 在被退课程列表中，自动切换到其他课程或清空
  • 清除 localStorage 中的 currentCourseId（如果指向被退课程）

2️⃣ 学习路径 (LearningPath) 严重

问题描述：退课后，该课程相关的 learning_paths 记录仍然存在，且状态可能是 ACTIVE。学生退课后再通过其他路由访问该课程的学习路径，数据仍然可查。

数据表：learning_paths（student_id + course_id）

-- 退课后，这些记录仍然存在且未改变状态 SELECT * FROM learning_paths WHERE student_id = 'xxx' AND course_id = 'yyy'; -- 结果可能返回 status = 'ACTIVE' 的路径

建议方案：

  • 后端：退课时，将该学生在该课程下的所有 ACTIVE/DRAFT/PAUSED 状态的学习路径统一标记为 PAUSED，或者在 PathStatus 中新增 DROPPED 枚举值（需要评估迁移成本）
  • 路径节点数据保留（作为历史记录），但路径不再活跃
  • 如果学生重新选课，可提供"恢复之前的学习路径"选项

3️⃣ 智能答疑 (QATutoring) 高

问题描述：QA 系统存在两层问题：

  • 数据层：chat_history 表没有 course_id 字段，无法区分对话属于哪个课程
  • 逻辑层：退课后，前端课程切换器不再显示该课程，QA页面也无法再基于该课程提问（因为 selectedCourseId 变了），但 histórico 中仍保留该课程的对话
-- chat_history 表结构（缺少 course_id） CREATE TABLE chat_history ( id UUID PRIMARY KEY, user_id UUID NOT NULL, -- FK → users knowledge_point_id UUID, -- 可空 session_id UUID NOT NULL, role VARCHAR(16) NOT NULL, ... -- ❌ 没有 course_id 字段 );

建议方案：

  • 数据库：为 chat_history 表添加 course_id 字段（可空，向下兼容）
  • 后端：QA 问答时保存 course_id 到每条消息
  • 前端：按课程隔离对话列表，退课后该课程的对话历史可查看但不能继续提问

4️⃣ 答题提交 (AnswerService) 高

问题描述：AnswerService.submitAnswer() 没有验证学生当前是否还选着该课程。退课后学生理论上不应再继续做题（因为没有该课程的入口了），但如果直接调用API，仍然可以提交答案，产生新的答题记录和错题记录。

@Transactional public SubmitAnswerResult submitAnswer(UUID studentId, SubmitAnswerRequest request) { Question question = questionRepository.findById(request.getQuestionId())...; // ❌ 缺少选课状态检查 boolean isCorrect = checkAnswer(question, request.getStudentAnswer()); // 保存答题记录（携带 courseId） AnswerRecord record = new AnswerRecord(); record.setStudentId(studentId); record.setCourseId(question.getCourseId()); ... // 答错 → 创建错题记录 if (!isCorrect) { createErrorRecord(studentId, question, request.getStudentAnswer()); } // 答对 → 推进学习路径节点 if (isCorrect && question.getCourseId() != null) { advanceLearningPathNode(studentId, question.getCourseId(), question.getKnowledgePointId()); } ... }

建议方案：

  • 在 submitAnswer() 开头增加选课状态校验：
// 检查学生是否已选该课程（且为 active 状态） boolean enrolled = studentCourseRepository .existsByStudentIdAndCourseIdAndStatus(studentId, question.getCourseId(), "active"); if (!enrolled) { throw new ValidationException("您尚未选课或课程已退课"); }

5️⃣ 学情总览 (StudentDashboard) 中

问题描述：仪表盘依赖 selectedCourseId 查询诊断数据。退课后切换到其他课程，仪表盘显示新课程的数据，表现正常。但如果学生没有其他可选课程，selectedCourseId 为空，仪表盘显示"请先选择一门课程"。

影响：功能上无数据异常，但用户体验上，退课后如果只剩一门课，应该自动切换到那门课；如果无课可选，应该引导去选课。

建议方案：

  • 退课后联调到选课列表刷新逻辑
  • MainLayout 中当 studentCourses 列表变化时，自动校验当前 selectedCourseId 是否有效

6️⃣ 错题复盘 (ErrorReview) 中

问题描述：error_records 表 V7 已添加 course_id 字段，前端已按 selectedCourseId 过滤。退课后切换到其他课程，不再显示已退课程的错题。

需要决策的问题：

  • 数据保留策略：退课后的错题数据是保留还是软删除？
  • 重新选课场景：如果学生后续重新选修同一门课，历史错题是否应该恢复可见？
  • 独立查看：是否需要一个"历史课程"入口，让学生可以查看已退课程的错题？

建议方案：

  • 错题数据应该保留（这是学习轨迹的重要组成部分）
  • 退课后不删除，但默认不显示在错题列表中
  • 如果学生重新选课，自动恢复可见
  • 长期可考虑增加"历史课程"筛选器

7️⃣ 我的课程 (StudentCourses) 低

问题描述：退课后，listByStudent 查询 findByStudentIdAndStatus(studentId, "active")，不返回已退课程，前端列表显示正常。退课按钮上的 Popconfirm 提示"学习进度将被保留"也符合当前软删除策略。

需要增强：

  • 退课成功后，应该主动通知 MainLayout 刷新课程列表和 selectedCourseId
  • 可以增加"退课记录"查询接口，让学生查看历史选课记录

8️⃣ 学习会话 (StudySessions) 低

问题描述：study_sessions 表没有 course_id 字段，仅有 learning_path_node_id 间接关联课程。退课后历史会话数据保留，但不会再创建新的会话（因为前端没有入口）。

建议方案：

  • 低优先级，当前影响不大
  • 长期可考虑添加 course_id 字段以便按课程统计学习时长

EnrollmentService.dropCourse 增强版

@Transactional public void dropCourse(UUID enrollmentId) { StudentCourse sc = studentCourseRepository.findById(enrollmentId) .orElseThrow(() -> new ResourceNotFoundException("选课记录", enrollmentId)); // 1. 标记退课 sc.setStatus("dropped"); studentCourseRepository.save(sc); // 2. 🔗 联动：暂停该课程下的所有学习路径 UUID studentId = sc.getStudentId(); UUID courseId = sc.getCourseId(); List<LearningPath> paths = learningPathRepository .findByStudentIdAndCourseId(studentId, courseId); for (LearningPath path : paths) { if (path.getStatus() == PathStatus.ACTIVE || path.getStatus() == PathStatus.DRAFT) { path.setStatus(PathStatus.PAUSED); } } learningPathRepository.saveAll(paths); log.info("退课成功: enrollmentId={}, 已暂停 {} 条学习路径", enrollmentId, paths.size()); }

🎯 总结

退课（dropCourse）当前是一个孤立操作，只修改了选课表本身的状态。由于 EduMentor 的多个功能模块（学习路径、智能答疑、错题复盘等）都依赖于"学生-课程"的映射关系，退课需要触发一系列联动操作来维持数据一致性。

核心原则：

  1. 历史数据保留 — 答题记录、错题记录、对话历史等学习轨迹数据应当保留
  2. 活跃状态暂停 — 学习路径等活跃资源应当暂停，而非删除
  3. 前端上下文同步 — 退课后前端上下文（selectedCourseId）必须立即刷新
  4. API层防护 — 退课后后端应当拒绝该课程的答题提交等写操作
  5. 可恢复性 — 同学生重新选同一门课时，历史数据应当恢复可见
