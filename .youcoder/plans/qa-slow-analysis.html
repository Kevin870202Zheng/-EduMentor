🔍 智能答疑辅导 — 响应慢原因分析报告

基于对整个调用链路的全面代码审计，识别出以下性能瓶颈。按影响程度从高到低排列。

📊 一句话总结

RAG 上下文和对话历史被无意义地加载了两次、@Transactional 在流式输出全程锁住数据库连接、对话历史全量加载不做分页 — 这三个问题是当前配置下最主要的性能杀手。如果将来切换到向量引擎（VectorRAGEngine），还会面临 Embedding API 被重复调用 的额外问题。

二、性能瓶颈详细分析

🚨 瓶颈1：RAG 检索被重复调用两次

P0 严重

问题代码：QAService.java:163-164

// 第 163 行：第一次检索 — 取 top 5 构建 RAG 上下文
String ragContext = buildRagContext(question, request);

// 第 164 行：第二次检索 — 取 top 3 构建来源信息
List<SourceInfo> sources = buildSources(question, request);

影响分析：

  • 当前 MockRAGEngine 下：虽然只是内存关键词匹配，每次约 10-50ms，但两次独立调用浪费了 10-50ms 的无谓开销
  • 将来切换到 VectorRAGEngine 后：两次独立的 Embedding API HTTP 调用（每次 200-500ms）+ 两次全量余弦相似度计算（每次 50-200ms），总计浪费 500ms-1.4s

根本原因：buildRagContext 和 buildSources 各自独立调用 RAG 引擎，传入的参数不同（topK=5 vs topK=3），无法共享检索结果。

修复方案：合并为一次 RAG 检索，取 top 5 结果，将前 3 个用于 sources，全部 5 个用于 context。

🚨 瓶颈2：@Transactional 长时间占用数据库连接

P0 严重

问题代码：QAService.java:153

@Transactional  // ← 整个流式输出过程都持有数据库连接！
public void streamAsk(ChatRequest request, UUID userId, 
                      Consumer<LLMResponse> chunkConsumer) {
    // ... LLM 流式调用可能持续 30s ~ 2min ...
    // 数据库连接一直被占用不释放
}

影响分析：

  • @Transactional 会在方法开始时从连接池获取连接，在方法结束时才释放
  • LLM 流式调用可能持续 30秒~几分钟，连接被长期占用
  • 在并发场景下，数据库连接池（通常 10-20 个连接）很快耗尽
  • 其他请求（如获取会话列表、课程列表等）因拿不到连接而排队等待

修复方案：将 @Transactional 移到只写数据库的地方（saveMessage），主流程使用编程式事务。

⚠️ 瓶颈3：对话历史全量加载，不做 LIMIT 分页

P1 高

问题代码：QAService.java:347-352

private String buildHistoryContext(String sessionId) {
    // ← 全量加载所有历史消息！
    List<ChatHistory> recentMessages = chatHistoryRepository
            .findBySessionIdOrderByCreatedAtAsc(sessionId);

    // 后续才取最近 10 轮
    int startIndex = Math.max(0, recentMessages.size() - MAX_HISTORY_ROUNDS);
    List<ChatHistory> contextMessages = recentMessages.subList(startIndex, ...);
}

影响分析：

  • 如果会话历史很长（50+ 轮对话），每次查询都会从数据库加载 全部消息记录 到内存
  • 数据量大的情况下：数据库查询变慢 + 网络传输延迟 + Java 对象创建 GC 压力
  • 实际只需要最近 10 轮（共 20 条消息），完全可以 SQL 级别限制

修复方案：在 Repository 中添加带 Pageable 或 LIMIT 的查询方法。

⚠️ 瓶颈4：buildSources 未使用 courseId 过滤

P1 高

问题代码：QAService.java:322-326

List<RAGEngine.SourceInfo> ragSources;
if (request.getKnowledgePointId() != null) {
    ragSources = ragEngine.retrieveSources(question, 3);  // ← 没传 courseId
} else {
    ragSources = ragEngine.retrieveSources(question, 3);  // ← 没传 courseId
}

对比一下 buildRagContext 的正确做法：

if (request.getCourseId() != null) {
    return ragEngine.buildEnhancedContext(question,
            request.getCourseId().toString(), 5);  // ✅ 传了 courseId
}

影响分析：当前 MockRAGEngine 下影响不大（内存关键词扫描），但切换到 VectorRAGEngine 后，findAll() 全表扫描 + 全量余弦计算，数据量大时会非常慢。

📌 瓶颈5：Prompt Tokens 过大

P2 中

问题代码：QAService.java:77, 347-363

private static final int MAX_HISTORY_ROUNDS = 10;  // 10 轮对话 = 20 条消息

影响分析：

  • 每次请求的 Prompt 由三部分拼接：系统提示词 + RAG 上下文 + 历史对话（最多 20 条消息）
  • 如果 RAG 返回 5 个长文档片段 + 10 轮历史对话，Prompt 很容易超过 4000-8000 tokens
  • Prompt tokens 越多，首 token 生成时间（TTFT） 越长：DeepSeek 模型是 Decoder-only 架构，TTFT 与 Prompt 长度近似线性增长
  • 且每次流式回复完成后，后续提问的 Prompt 会进一步累积历史对话

📌 瓶颈6：Embedding Service 未使用连接池

P2 中

问题代码：EmbeddingService.java:37

public EmbeddingService(EmbeddingConfig config) {
    this.config = config;
    this.webClient = WebClient.builder().build();  // ← 无连接池，无超时配置
}

影响分析：虽然当前 MockRAGEngine 未使用 Embedding，但将来启用 VectorRAGEngine 后，每次 Embedding API 调用都需要重新建立 TCP 连接（包括 TLS 握手），增加 100-300ms 的延迟。建议使用 HttpClient.create().connectionProvider(...) 配置连接池。

📌 瓶颈7：前端 SSE 中 JSON 转义增加解析开销

P3 低

问题代码：QAController.java:109-111 + api.jsx:197-199

// 后端：手动拼接 JSON + escapeJson
emitter.send(SseEmitter.event()
    .name("chunk")
    .data("{\"content\":\"" + escapeJson(response.getContent()) + "\"}"));

// 前端：解析 JSON
const parsed = JSON.parse(jsonStr);  
onChunk?.(parsed.content || '');

影响分析：后端手动 escape JSON，然后前端再 parse，每段内容都要经历一次序列化/反序列化。虽然每个 chunk 很小所以影响不大，但换成 Jackson 序列化会更干净高效。属于优化点而非瓶颈。

四、根因总结

优先级 问题 影响 修复成本
P0 RAG 检索被重复调用两次 Vector 下浪费 500ms-1.5s 低（合并两次调用）
P0 @Transactional 全程锁连接 并发时连接池耗尽，其他请求阻塞 低（改为编程式事务）
P1 对话历史全量加载 长会话下查询慢 + 内存浪费 低（加 LIMIT 分页）
P1 buildSources 没传 courseId Vector 下全表扫描 低（加参数判断）
P2 Prompt tokens 持续累积 TTFT 随对话轮次增长 中（压缩/截断历史）
P2 Embedding 无连接池 每次连接握手 100-300ms 低（配置连接池）
P3 后端手动 escape JSON 微小解析开销 低（Jackson 序列化）

五、推荐修复方案

修复1：合并 RAG 检索（P0）

在 QAService.streamAsk() 中改为一次 RAG 检索，结果分给 context 和 sources：

// 一次性检索，取 top 5（需要较多上下文给 LLM）
List<DocumentChunk> docs = ragEngine.retrieveByCourse(question, courseId, 5);
String ragContext = formatToContext(docs);               // 全部5条 → RAG 上下文
List<SourceInfo> sources = formatToSources(docs, 3);     // 取前3条 → 来源展示

修复2：移除 @Transactional（P0）

改为仅对 saveMessage 使用编程式事务：

public void streamAsk(...) {   // 移除 @Transactional
    // 非事务环境：数据库操作
    saveMessage(..., question, null, null);  // 自动提交

    // LLM 流式调用 — 不持连接
    llmService.askStream(systemPrompt, question, response -> { ... });

    // 完成时保存
    saveMessage(..., fullAnswer, tokens, metadata);  // 自动提交
}

修复3：对话历史加 LIMIT（P1）

添加分页查询方法：

@Query("SELECT h FROM ChatHistory h WHERE h.sessionId = :sessionId " +
       "ORDER BY h.createdAt DESC")
List<ChatHistory> findRecentBySessionId(@Param("sessionId") String sessionId,
                                        Pageable pageable);

修复4：buildSources 传 courseId（P1）

让 buildSources 也使用 retrieveSources(question, courseId, 3)，与 buildRagContext 对齐。

修复5：对话历史上下文截断（P2）

除了限制轮次（已做），还应该限制上下文的总字符数，超过时丢弃最早的历史：

private static final int MAX_HISTORY_CHARS = 2000;  // 历史上下文硬限制

六、预期效果

完成上述 P0+P1 修复后：

  • MockRAGEngine：每轮问答节省约 20-100ms（消除重复检索 + 消除全量历史加载）
  • VectorRAGEngine：每轮问答节省约 500ms-1.5s（减少一次 Embedding API 调用 + 减少一次全量余弦计算）
  • 并发场景：数据库连接不再被长时间占用，连接池压力大幅降低
  • 长会话场景：后续提问不会因为历史累积而越来越慢
