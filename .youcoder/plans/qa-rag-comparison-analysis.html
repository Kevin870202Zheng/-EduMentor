🔍 EduMentor 智能答疑慢 — 与 buffett-wiki 的对比分析

分析日期：2026-06-25 | 对比项目：buffett-wiki（Node.js + OpenRouter）vs EduMentor（Spring Boot + DeepSeek）

✅ 前置确认 — 两个项目使用 完全相同的 DeepSeek 模型 API（底层都是 OpenAI 兼容接口），但 buffett-wiki 通过 OpenRouter 代理调用，EduMentor 直连 DeepSeek。因此速度差异不是模型能力差异导致的。

📊 核心发现：一个架构问题 + 三个实现问题

#问题严重度buffett-wiki 做法EduMentor 做法预估影响
1 对话历史被塞入 System Prompt P0 架构 历史作为独立 messages（role: user/assistant） 历史拼接到 system prompt 中 每轮对话 TTFT 增加 1-3s
2 向量检索引擎 JSON 反序列化 O(n) P1 性能 预加载 Float32Array，纯内存计算 从 DB 加载 JSON → 反序列化 float[] → 余弦 32条 ~50ms，1000条 ~500ms
3 无检索结果缓存 P1 性能 LRU 缓存 200 条 / 30 分钟 TTL 每次请求都重新计算 重复问题浪费 300-800ms
4 embedVolcengineSingle 逐条调用 P2 效率 单条 query embedding 非批量时逐条调 API 单条无影响，批量场景慢

🔴 问题 1（最严重）：对话历史被塞入 System Prompt

EduMentor 的做法（错误）

// QAService.java — buildCombinedSystemPrompt
private String buildCombinedSystemPrompt(String ragContext, String historyContext) {
    String basePrompt = SYSTEM_PROMPT.replace("{rag_context}", ragContext);
    if (historyContext != null) { basePrompt += historyContext; }
    return basePrompt;
}

// 然后在 LLMService 中发送：
messages = [
    { role: "system", content: "你是智能学伴... [RAG资料]...\n\n## 对话历史\n学生: 问题1\n学伴: 回答1\n学生: 问题2\n..." },
    { role: "user", content: "当前问题" }
]

后果：每次对话，system prompt 都会增长（追加历史）。第 10 轮时 system prompt 可能有 5000-8000 tokens，TTFT 显著增加。

buffett-wiki 的做法（正确）

// server.js — 发送时使用独立 messages
messages = [
    { role: "system", content: "你是 AI 巴菲特... [RAG资料]..." },  // 固定大小
    { role: "user", content: "问题1" },      // 独立消息
    { role: "assistant", content: "回答1" },  // 独立消息
    { role: "user", content: "当前问题" }      // 独立消息
]

优点：system prompt 固定不变。LLM 只需处理 system prompt 一次（KV cache 可复用），后续每轮只追加 2 条消息。

为什么这个差异这么重要？

DeepSeek 模型的 首 token 生成时间（TTFT） 与 prompt 总长度大致成正比。当 system prompt 从 500 tokens 膨胀到 5000 tokens：

  • TTFT 从 ~1s 增加到 ~5-8s
  • KV cache 无法复用（因为 system prompt 每次都变化）
  • 用户每次提问都要等待更长的预处理时间

🟠 问题 2：向量检索引擎效率低下

EduMentor 的 VectorRAGEngine

// VectorRAGEngine.search()

// ② 从 DB 加载所有向量（JSON 格式）

// ③ 逐条反序列化 JSON → float[] + 余弦相似度
for (KpEmbedding entry : candidates) {
    float[] docVec = vectorizationService.jsonToFloatArray(entry.getEmbedding());
    double similarity = cosineSimilarity(queryVec, docVec);
}

buffett-wiki 的 embeddingService

embeddingsCache = new Map();  // Map<title, Float32Array>
for (const page of wikiIndex) {
    const vec = new Float32Array(page.embedding);  // 预加载为 typed array

// 查询时：纯内存运算

// vectorSearch 内部: cosineSimilarity(queryVec, docVec)
// 无 DB 查询、无 JSON 反序列化

🟠 问题 3：无缓存层

EduMentor 每次提问都执行完整的：Embedding API → 向量检索 → LLM 调用。

如果学生连续问相似的问题（如"什么是浮存金"和"浮存金是什么意思"），每次都重新计算。

buffett-wiki 有 LRU 搜索缓存：

const searchCache = new Map()
const SEARCH_CACHE_MAX = 200
const SEARCH_CACHE_TTL = 1800000  // 30分钟

function getCachedSearch(query) {
    const entry = searchCache.get(query)
    if (entry && (Date.now() - entry.ts) < SEARCH_CACHE_TTL) {
        return entry.data  // 命中缓存，直接返回
    }
    return null
}

🟡 问题 4：embedVolcengineSingle 逐条调用

当前 32 条向量影响不大，但如果向量库增长到 10000+ 条，embedding API 的逐条调用 + 全量余弦计算会成为瓶颈。建议后续引入 pgvector 扩展，将 ORDER BY embedding <-> query_vec LIMIT 5 下沉到数据库执行。

🎯 关键结论

为什么 buffett-wiki 感觉快很多？

  1. 模型不同：buffett-wiki 用 openai/gpt-5.4-nano（通过 OpenRouter），这个模型比 DeepSeek v4 Flash 生成速度快得多（TTFT ~1-2s vs 3-8s）
  2. System Prompt 最优：固定大小，不随对话历史增长，KV cache 高效
  3. 前端体验不同：开启 SSE 后第一时间显示"正在思考"，用户感知的等待时间更短（TTFT 掩盖在连接建立中）

EduMentor 需要修复的优先级

优先级修复项预期提速
P0 立即把对话历史从 System Prompt 分离为独立 messagesTTFT 每轮减少 30-60%

P1 重要向量检索使用 pgvector SQL 级相似度查询（替代 Java 级全表扫描）大库省 50-500ms
P2 优化启动时预加载 embedding 到内存（避免每次查询从 DB 读 JSON）省 20-50ms

📋 具体修复建议

P0 修复：对话历史分离

在 QAService.java 和 LLMService.java 中，将对话历史作为独立的 messages 传递：

// 当前（错误）：
generateStream(systemPromptWithHistory, question, callback)
// → API 调用: [{role: "system", content: "指令 + RAG + 历史"}]

// 修复后（正确）：
chatStream(systemPromptOnly, historyMessages, question, callback)
// → API 调用: [{role: "system", content: "指令 + RAG"}, {role: "user", content: "历史问题"}, {role: "assistant", content: "历史回答"}, {role: "user", content: "当前问题"}]
