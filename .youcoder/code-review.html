🔴 严重问题

严重 Token 刷新逻辑中字段名不匹配，刷新完全不可用
📄 frontend/src/services/api.jsx 第 54 行
Token 刷新时，从响应中提取新 token 的字段名错误。后端 refresh 端返回 { code, data: { accessToken, refreshToken } }， 但前端读取 res.data?.data?.token（应为 accessToken）。 
// ❌ 当前代码（读取不到 token）
const newToken = res.data?.data?.token || res.data?.token;
修复建议： 
// ✅ 修正后
const newToken = res.data?.data?.accessToken || res.data?.accessToken;
影响：Token 过期后前端尝试自动刷新，但永远获取不到新 token，导致用户被强制登出。

🟡 中等问题

中等 后端存在两套重复的 CORS 配置
📄 CorsConfig.java + SecurityConfig.java
CorsConfig 通过 WebMvcConfigurer 和 CorsFilter Bean 配置了 CORS， 同时 SecurityConfig 也通过 corsConfigurationSource() Bean 配置了 CORS。 这会导致 Spring Security 和 Spring MVC 各处理一次，可能造成意外行为。 
// CorsConfig.java — 方式1: WebMvcConfigurer
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) { ... }
    
    @Bean
    public CorsFilter corsFilter() { ... }  // 方式2: Filter
}

// SecurityConfig.java — 方式3: CorsConfigurationSource Bean
@Bean
public CorsConfigurationSource corsConfigurationSource() { ... }
修复建议：删除 CorsConfig.java 中的 @Configuration 和 addCorsMappings 方法， 仅保留 SecurityConfig 中的 corsConfigurationSource()，因为 Spring Security 会优先使用它。 CorsFilter Bean 也可删除，因为它与 Spring Security 的 CORS 处理会冲突。
中等 JwtAuthFilter 每次请求都查询数据库，影响性能
📄 JwtAuthFilter.java 第 54 行
新修改的代码在每次认证请求时都通过 userRepository.findById(userId) 查询数据库获取 User 实体。 对于高并发场景，这会额外增加数据库压力。 
// 每次请求都查库
Optional<User> userOpt = userRepository.findById(userId);
User user = userOpt.get();
修复建议（二选一）：
  1. 方案A（推荐）：JWT 中已包含 userId + role，可将 principal 设为 UserSummary 轻量对象（仅 id + role + username），无需查库
  2. 方案B：引入 Caffeine 缓存 User 实体，设置合适的过期时间
中等 前端两套 API Client 系统并存，Token Key 不统一
📄 api.jsx vs apiClient.ts
系统Token Key使用方
services/api.jsx（旧）edumentor_tokenAuthContext, 所有页面组件
api/apiClient.ts（新）edumentor_access_tokenTypeScript API 模块（未被使用）
两套系统互不兼容，新 apiClient 写的 token 不会被旧系统读取到。目前旧系统在使用中，新系统（TypeScript）处于"死代码"状态。
建议：统一使用一套系统。如果计划使用 TypeScript 版，需要逐步迁移； 如果继续用旧系统，建议删除未使用的 TypeScript API 模块减少维护成本。

🔵 建议/低优先级

建议 api.jsx refresh 请求参数名与后端不一致
📄 frontend/src/services/api.jsx 第 51-52 行
前端发送 { refresh_token: refreshToken }（snake_case）， 需确认后端 RefreshTokenRequest DTO 的字段名。如后端使用 refreshToken（camelCase），会导致参数绑定失败。
建议：查看后端 RefreshTokenRequest DTO 确认字段名，保持一致。
建议 StudentDashboard 硬编码课程 ID
📄 frontend/src/pages/StudentDashboard.jsx 第 16 行
const DEMO_COURSE_ID = '1';
课程 ID 是硬编码字符串，在真实多课程场景下不可用。建议从 URL 参数或用户设置中获取。
建议 Login 页面缺少对登录错误的展示
📄 frontend/src/pages/Login.jsx + AuthContext.jsx
AuthContext.login 中的错误直接向外抛出，但 Login 页面的 handleLogin 没有 catch 错误并展示给用户。 如果用户输入错误密码，页面没有反馈。
建议 nginx.conf 注释写的是 "Flask 后端"
📄 frontend/nginx.conf 第 57 行
# API 反向代理到 Flask 后端
实际后端是 Spring Boot，应修正注释。另外第 56 行的标题也提到 Flask，应同步修改。
建议 SecurityConfig 中 JWT 访问令牌过期时间冲突
📄 application.yml 第 41-42 行 vs docker-compose.yml 第 28 行
# application.yml（默认值）
jwt:
  access-token-expiration: 1800   # 30分钟
  refresh-token-expiration: 604800  # 7天

# docker-compose.yml（默认值，会覆盖）
JWT_ACCESS_TOKEN_EXPIRATION: ${JWT_ACCESS_TOKEN_EXPIRATION:-3600}  # 1小时
application.yml 默认 token 有效期 30 分钟，但 docker-compose 默认 1 小时。 部署时实际使用的是 docker-compose 的值（1 小时），与配置文件不一致。建议统一。
建议 GlobalExceptionHandler 日志级别不统一
📄 GlobalExceptionHandler.java
大部分异常处理使用 log.warn，但最后的兜底 Exception.class 使用 log.error。 JwtAuthFilter 的异常（如 JWT 过期）是预期行为，建议也将日志级别从 log.debug 调整为 log.warn 以便排查问题。
